### PR 1 — `fix/unmapped-mate-minaqual` — "Apply the -a MAPQ cutoff to aligned mates only in htseq-count"

Closes #NNN

`_assess_pe_read` in `HTSeq/scripts/count_features/count_features_per_file.py`
(and the same test in `htseq-count-barcodes`) compared the MAPQ of both
records of a pair with `--minaqual` without checking that the record is
aligned. Aligners write MAPQ 0 on the record of an unmapped mate, so a pair
whose mate is unmapped but present in the file was counted as
`__too_low_aQual` under the default `-a 10`, while the same pair was counted
for its gene when the unmapped record was absent from the file — and while
the FAQ says that only the aligned read determines how such a pair is
counted.

This checks `aQual` only for aligned mates. Pairs with both mates aligned,
single-end reads and the `-a 0` setting are unchanged.

- Test: `test/test_htseq-count.py::HTSeqCount::test_pair_with_unmapped_mate_is_counted`
  writes a three-pair BAM with pysam (mate unmapped in file / mate absent /
  both mapped) and expects `A 3`, `__too_low_aQual 0`; it fails on `main`
  (`'2' != '3'`) and passes with the fix. `test/test_htseq-count.py` and
  `test/test_parsers.py`: 41 passed, 5 skipped with the patch (the skips need
  loompy/anndata), same as on `main`.
- `doc/history.rst`: entry added.

**Behaviour change to flag in review:** with this patch, paired-end runs on
BAM files that keep unmapped mates (HISAT2, BWA, Bowtie2 defaults; STAR with
`--outSAMunmapped Within`) will count those pairs for their genes instead of
listing them under `__too_low_aQual`, so gene counts rise by the number of
one-mate-unmapped pairs and `__too_low_aQual` falls by the same number.

### PR 2 — `fix/bam-reader-interval-offset` — "Fix BAM_Reader[iv] fetching from iv.start + 1 instead of iv.start"

Closes #NNN

`BAM_Reader.__getitem__` called `pysam.AlignmentFile.fetch(iv.chrom,
iv.start + 1, iv.end)`. pysam's `fetch` takes 0-based, half-open coordinates,
the same convention as `GenomicInterval`, so the window was shifted right by
one base and an alignment whose last aligned base is `iv.start` was not
returned although `iv.overlaps(alignment.iv)` is `True`. This passes
`iv.start`.

- Test: `test/test_parsers.py::test_bam_reader_getitem_window` writes a
  five-read BAM with pysam and expects exactly the three reads overlapping
  `chr1:[100,200)`, cross-checked against `GenomicInterval.overlaps`; it
  fails on `main` (the read aligned to `[91,101)` is missing) and passes with
  the fix. `test/test_parsers.py` and `test/test_genomic.py`: 20 passed,
  1 skipped with the patch (the skip needs pyBigWig), same as on `main`.
- `doc/history.rst`: entry added.

`htseq-count` does not use this method; the TSS tutorial
(`doc/tutorials/tss.rst`) does.

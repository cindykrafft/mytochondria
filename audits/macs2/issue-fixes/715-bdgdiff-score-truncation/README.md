# MACS issue #715 — bdgdiff truncates region scores to integers

_Issue-fix round for the MACS2/MACS3 audit (`../../README.md`). Prepared 2026-09-03 against
`macs3-project/MACS` `main` at `c18cc244b2e22b578535d8dd8d150995657b7341` ("remove cykhash and use
python dictionary for speed", 2026-07-06; `macs3 --version` = 3.0.5beta). Note: the repository's
default branch is `main`, not `master`._

## The issue

**#715 — "Bug: macs3 bdgdiff produces scores less than -C cutoff in cond1/2 bed file, and scores
of all zeroes in common bed file"** — https://github.com/macs3-project/MACS/issues/715, opened
2025-11-17, label Bug Report, 0 comments, MACS 3.0.3.

Reporter's claim: running `macs3 bdgdiff ... -C 0.2` gives regions in `*_cond1.bed`/`*_cond2.bed`
whose score column is below the cutoff, and every score in `*_common.bed` is 0; expected scores
≥ cutoff in cond1/cond2 and small non-zero values in common. (The screenshot in the issue could
not be viewed from this session; the body alone is enough.)

## Diagnosis (file:line on `main` c18cc24)

`MACS3/Signal/ScoreTrack.py:1930` `TwoConditionScores.mean_from_peakcontent` computes the
length-weighted mean of the per-interval log10 likelihood ratios that becomes the BED score of a
bdgdiff region (`__add_a_peak`, line 1855). It declares

```
1938        tmp_v: cython.long
1939        sum_v: cython.long      # for better precision
...
1948            tmp_v = peakcontent[i][2]
```

so each float log10LR is converted to a C `long` (truncated toward zero) before `sum_v += tmp_v *
(tmp_e - tmp_s)`. In MACS2 2.2.9.1 (`MACS2/IO/ScoreTrack.pyx:1702-1722`) and MACS3 3.0.0
(`MACS3/Signal/ScoreTrack.pyx:1419-1440`) both variables were `float64_t tmp_v, sum_v  # for better
precision`; the pure-Python-mode rewrite (present in the 3.0.3 sdist, `ScoreTrack.py:1824-1825`)
turned them into `cython.long`, apparently misreading the "better precision" comment.

Effect: cond1/cond2 scores are the mean of the integer parts of the log10LRs (a score of 0.33
becomes 0, 6.18 becomes 6), and the common file, whose |log10LR| ≤ cutoff by construction, is all
zeros whenever the cutoff is below 1 — exactly #715. With the default `-C 3` every score is biased
low by up to 1.

**Fix** (`0001-bdgdiff-do-not-truncate-region-scores-to-integers.patch`, branch
`fix/issue-715-bdgdiff-score-truncation`): declare `tmp_v` and `sum_v` as `cython.double` (two
lines). The commit also repairs the `Test_TwoConditionScores.setUp` fixture in
`test/test_ScoreTrack.py`, which called `bedGraphTrackI.safe_add_loc` (removed on `main`; the class
had no test methods so the broken fixture never ran), and adds a regression test.

## Reproduction (`repro.py`, run with `python repro.py <MACS checkout> macs3`)

Part 1 — four synthetic tracks, `macs3 bdgdiff --d1 1 --d2 1 -C 0.2 -l 200 -g 100`, where the
cond1 intervals have log10LR(t1 vs t2) = 0.3271 and 6.1784 (pseudocount 0.01):

| | `main` (`repro.before.out`) | fixed (`repro.after.out`) |
|---|---|---|
| cond1 score | **3.0** (= (0 + 6) / 2) | **3.25276** (= (0.3271 + 6.1784) / 2) |

Part 2 — the project's own `test/cmdlinetest` step 10 (two `callpeak -B` runs on the CTCF chr22
50k test data, then `bdgdiff` with defaults) compared with `test/standard_results_bdgdiff/`:

| | `main` | fixed |
|---|---|---|
| cond1 regions | 638 (coordinates identical to reference) | 638 |
| scores differing from reference | **638 / 638** (24.9521 / 36.903 / 48.8178 vs 25.5431 / 37.3104 / 49.3307) | **0 / 638** |

So the reference files were generated by a float-correct build and the fix restores them exactly;
no reference needs regenerating. `cmdlinetest` did not catch the regression because BED files that
differ are accepted when their Jaccard index is > 0.99 (`test/cmdlinetest`, "compare with standard
outputs"), which only looks at coordinates.

## Held findings noticed while reproducing (not in this PR; for separate issues per step 5)

1. **bdgdiff regions are displaced by one bedGraph interval** (`interval_shift_probe.py`).
   `build_chromosome` stores each interval's *start* (`ScoreTrack.py:1511`, `self.add(chrname,
   pre_p, ...)`) but `call_peaks` reads the stored positions as *ends* (`:1812` `endpos =
   pos[cat1]`, `:1814` `startpos = pos[cat1-1]`). On the synthetic tracks the cond1 intervals span
   1000–3000 and the region reported is chr1:0–2000; the common interval [0,1000) is dropped (index
   0 → zero-length region). The same statements are in MACS2 2.2.9.1 (`ScoreTrack.pyx:1414,
   1642-1643`) and MACS3 3.0.0 (`:1120, 1356-1357`), so this is long-standing and the shipped
   reference outputs carry it. It changes every bdgdiff coordinate, so it needs the maintainers'
   confirmation before a PR.
2. **`macs3 bdgopt -m p2q` does not apply Benjamini–Hochberg.** `bedGraphTrackI.p2q`
   (`BedGraph.py:904`) has the rank increment commented out (`:973 # k += l`; `:974 nhcal += 1`
   instead), so q-score = max(0, p-score − log10 N) for every value — a Bonferroni-like
   correction — whereas `CallPeakUnit.py:830/1002` and `ScoreTrack.make_pq_table` advance `k`.
   Probe: p-scores 6.0 / 2.0 / 0.5 over 100 / 300 / 600 bp give BH q-scores 3.000 / 1.004 / 0.103
   but `p2q` returns 3.000 / 0 / 0. The documentation (`docs/source/docs/bdgopt.md`) promises "the
   Benjamini-Hochberg process". One-line fix; no user report found.

## Caveats

- The regression test asserts the score only; it deliberately does not assert the region
  coordinates, which would bake held finding 1 into the test.
- The cast in the original code went through `float64_t`; the fix uses `cython.double` for both
  the accumulator and the term, and the returned value stays `cython.float`, matching 3.0.0.

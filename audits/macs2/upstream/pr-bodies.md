### PR 1 — `fix/keepdup-auto-control-threshold` — "callpeak: filter the control with its own duplicate threshold"

Closes #NNN.

With `--keep-dup auto`, `cal_max_dup_tags()` is computed separately for the control and its value is logged ("max_dup_tags based on binomial = N"), but the control was then filtered with the treatment's threshold: `control_max_dup_tags` was never used. This change uses it in `control.filter_dup()` and in the two log lines and two xls-header lines that reported the treatment's threshold as the control's.

**Before and after** (MACS3 3.0.5 built from main c544319; the synthetic treatment/control BEDs from the issue, treatment threshold 1, control threshold 3):

| | control reads kept (of 60,000) |
|---|---|
| before | 48,636 (filtered at 1, while the log says 3) |
| after | 59,706 (filtered at 3, as logged) |

Behaviour is unchanged for `--keep-dup all` and for numeric `--keep-dup` values, where both thresholds are equal. Output changes only for `--keep-dup auto` runs with a control whose depth differs enough from the treatment's for the two binomial thresholds to differ.

### PR 2 — `fix/poisson-lower-tail-init` — "Prob: restore the k=0 term in the large-lambda lower-tail Poisson CDF"

Closes #NNN.

See the companion issue: `__poisson_cdf_large_lambda` sums the lower-tail CDF from i=1, so the k=0 term is never added (MACS 1.4 seeded the sum with it; the MACS2 Cython port lost the line and read `cdf` uninitialised; MACS3 initialises it to 0 but still omits the term). This restores the 1.4 initialisation. No number MACS reports changes today: the function asserts lambda > 700, where the term is negligible, and no current command reaches it.

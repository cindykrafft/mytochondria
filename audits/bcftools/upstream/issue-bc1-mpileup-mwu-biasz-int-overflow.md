Title: mpileup: INFO/MQBZ, BQBZ, RPBZ, SCBZ, MQSBZ, NMBZ shrink towards zero once a quality bin holds 1291 or more reads (32-bit overflow of the tie correction)

<!-- samtools/bcftools has no issue template; README.md asks for bugs in the GitHub tracker -->

**Versions:** `develop` @ `7abcc0d6` (built with HTSlib `develop` @ `e503e04`), the 1.24 and 1.13 releases built from their tags. 1.10.2 and 1.9 do not have the Z-score annotations. Linux x86_64, gcc 13.3.0.

**What happens.** `calc_mwu_biasZ()` in `bam2bcf.c` accumulates the Mann-Whitney tie adjustment `t += (p*p-1)*p` with `int p` (and the pair counts `e`, `l`, `na`, `nb` in `int`). `p` is the number of reads (ref + alt, pooled over all samples) sharing one MAPQ, base-quality, position or soft-clip bin; the cube exceeds `INT_MAX` once `p >= 1291` and wraps, which inflates the variance and shrinks the Z score. Because MAPQ is capped at 59 for the histogram and BWA gives most reads MAPQ 60, bin 59 holds the whole reference depth of the site: this is reached at a single deep site with `-d` raised, and under the default `-d 250` in any multi-sample run once the summed reference depth passes 1290 (about 45 samples at 30x).

**Reproduction** (one reference, one SAM written by `awk`; script attached as `mcve_mpileup_mqbz_overflow.sh`, takes a bcftools path and the number of reference reads):

```sh
# 300-bp reference ACGTACGT..., site 150 is C; 1300 reference reads at MAPQ 60 and
# 40 reads with T at MAPQ 30, 50 bp each, sorted starts 101..149 so every read covers 150
sh mcve_mpileup_mqbz_overflow.sh ./bcftools 1300
```

Got (`develop`, 1.24, 1.13):

```
150	C	T,<*>	DP=1340 MQBZ=-7.88325
expected MQBZ=-36.5923 (U=0, mean=26000, tie-corrected var=504854.37)
```

Expected: −36.5923, the tie-corrected normal approximation the function implements (U = 0 since every alt read has lower MAPQ, mean = 1300·40/2, var = 1300·40/12·(1341 − T/(1340·1339)) with T = (1300³ − 1300) + (40³ − 40)); `scipy.stats.mannwhitneyu(..., method="asymptotic", use_continuity=False)` gives the same. With 1290 reference reads (1290³ still fits in 32 bits) the output is `MQBZ=-36.4555` = expected. Shrinking the example showed the condition is exactly "one bin with ≥ 1291 reads": the number of alt reads, the annotation (BQBZ with binned base qualities, e.g. 1,530 bases at Q37 gives −2.47 for a true −19.42) and the number of input files do not matter — 44 single-sample BAMs of 30 MAPQ-60 reads under the default `-d 250` give −6.97 for a true −36.73, and an int32-wrapped replica of the loop reproduces bcftools' value in every case. The score saturates around −11 at high counts (12,000 reads: −10.94 for a true −109.72), so a filter such as `MQBZ < -3` keeps mapping-quality artefacts at exactly the sites where the depth is highest. PL, AD, DP, QUAL and genotypes are unaffected.

**Proposed fix:** accumulate in `int64_t` (`e`, `l`, `na`, `nb`, `p`); 11 lines in `calc_mwu_biasZ`. A patch with a regression test (`test/mpileup/mwu-biasZ.1.bam`, 1,340 20-bp reads, 4.9 kB, run through `test/test.pl` with `-B -d 100000 -a -AD -r ref:150`; fails on unmodified `develop`, passes with the change) and a NEWS entry is ready; PR follows.

**On real data.** Two SARS-CoV-2 amplicon samples (nf-core/test-datasets `viralrecon`, `illumina/amplicon/sample1` and `sample2`, minimap2 to MT192765.1), run with the depth cap raised as viral pipelines do (`-d 1000000`): 2,934 and 1,749 of 29,829 positions hold more than 1,291 reads in one sample. On the sites with at least two alternate reads the current build and the 64-bit build differ at 328 and 769 sites for at least one of `MQBZ`, `BQBZ`, `RPBZ`, `SCBZ`, `MQSBZ`, and at 231 / 87 (`MQBZ`) and 141 / 118 (`BQBZ`) of them the two builds fall on different sides of a `< -3` filter, always with the current build closer to zero (position 948 of sample1, DP 1,618, 7 alternate reads: `MQBZ` −1.26 reported, −21.24 with 64-bit accumulators). Under the default `-d 250` with the two samples pooled no site reaches the bin size and every score is identical.

Title: Pairs whose fragment is slightly longer than -X get one mate reported with a spurious insertion instead of its exact alignment

<!-- BenLangmead/bowtie2 has no issue template. Fourth filing (report with mechanism; PR offered once the shape is agreed). Every version. Send after BW1 or BW2 has a reply. -->

**Versions:** 2.3.5.1, 2.4.2, 2.4.5, 2.5.1, 2.5.4 and `master` @ 58e34bf, identical numbers.

**What happens.** End-to-end mode, 100-bp mates that are exact copies of a random reference (so any gap in an alignment is wrong), ten pairs per fragment length, default options (`-X 500`):

```
fragment  concordant  discordant  mates with a gap   example mate CIGAR / AS / MAPQ      |TLEN| reported
 500-515     10 / 0        0-10          0             100M                                 true length
   520          0           10          10             91M5I4M   / -32 / 40                 515-518
   525          0           10          10             87M7I6M   / -50 / 23                 516-518
   530          0           10          10             84M12I4M  / -41 / 24                 513-518
 535-650        0           10           0             100M                                 true length
```

Every pair in the band from about `X + 18` to `X + 33` has one mate reported with a 2–12-bp insertion near its 3' end, `XS:i` absent, MAPQ 23–42, and a `TLEN` capped at about `X + 18`. The same happens at `-X 300` (band 320–330), with `--very-sensitive`, with `--no-discordant` (the gapped mate is then `YT:Z:UP`, MAPQ 0–23) and with `--no-mixed`; it does not happen in `--local` mode (the DP soft-clips instead). On a library of 6,000 pairs with fragment lengths ~N(380, 70) at the default `-X 500`, 50 of 12,000 mates come back with a false insertion (MAPQ 23 ×17, 24 ×17, 40 ×12, 42 ×4) and 50 pairs have a wrong `TLEN`; the same reads at `-X 1000` have no gap and exact `TLEN`s.

**Why.** After the anchor mate aligns, the opposite mate is sought by dynamic programming inside the window that `-I/-X` allow (`PairedEndPolicy::otherMate`, `pe.cpp`; the right edge is `off + maxfrag - 1`, widened by the number of gaps the minimum score permits). A fragment longer than `-X` by less than that allowance still has its mate partly inside the window, and the DP returns the best alignment that fits — the read's last bases go into an insertion so that the alignment ends at the window edge. `peClassifyPair` then correctly rejects the pair as non-concordant, but the gapped alignment has already been reported as the mate's unpaired alignment (`aligner_sw_driver.cpp`, `redMate2_.add(r2)` / `msink->report(0, NULL, r2)`). When the mate's own seed search later finds the exact alignment, which starts at the same reference position, `RedundantAlns::overlap` (`aligner_result.cpp`) declares it redundant — the two alignments share their first 90-odd (reference offset, read offset) cells — and it is discarded (`if(!red.overlap(r)) { red.add(r); msink->report(...) }`). The pair is reported as discordant with the gapped mate.

Scripts: `x1_maxins_boundary.py` (the scan above) and `x2_maxins_realistic_library.py` (the 6,000-pair library) in the repository linked below; both build their reference and reads and run any `bowtie2-align-s`.

**Possible fixes** — I would rather ask which shape you prefer before sending a PR: (a) do not report a rescue alignment as the mate's unpaired alignment when the pair it was found for is not concordant (let the mate's own search supply the unpaired alignment); (b) let the redundancy check keep the better-scoring of two alignments that share cells; or (c) reject rescue alignments whose gaps are forced by the window edge. Any of them keeps the concordant case unchanged, since the band only exists for fragments longer than `-X`.

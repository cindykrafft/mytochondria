Title: `threads=1` with `iterations <= 50` raises ZeroDivisionError

<!-- ventolab/CellphoneDB has no issue template; this follows the structure of a minimal
     complete verifiable example. -->

**Version:** 5.0.1 (PyPI wheel and `master` @ `dc8abd15`, byte-identical); introduced in v5.0.0
with the `threads == 1` branch (v4.0.0 has no such branch).

### Summary

The single-threaded branch of `shuffled_analysis`
(`cpdb_statistical_analysis_helper.py:479, 490`) computes a progress step and takes a modulus by
it:

```python
progress_step = round(iterations / 100, 0)
for i in range(iterations):
    ...
    if i % progress_step == 0:
```

`round(iterations / 100, 0)` is `0.0` for every `iterations <= 50` (0.5 rounds to 0 under
banker's rounding), so any run with `threads=1` and `iterations <= 50` dies before producing a
single result. `threads=1` is the workaround the comment immediately above this branch recommends
for driving the package from R/RStudio on Windows (referencing #102), where trying a small
`iterations` first is the natural thing to do.

### Minimal reproduction (no database needed)

```python
import numpy as np, pandas as pd
from cellphonedb.src.core.methods import cpdb_statistical_analysis_helper as helper

meta = pd.DataFrame({'cell_type': ['A', 'A', 'B', 'B']}, index=['c1', 'c2', 'c3', 'c4'])
counts = pd.DataFrame([[1.0, 2.0, 0.0, 3.0], [0.0, 1.0, 2.0, 2.0]],
                      index=[1, 2], columns=['c1', 'c2', 'c3', 'c4'])
interactions = pd.DataFrame({'multidata_1_id': [1], 'multidata_2_id': [2]}, index=[0])
combos = np.array([['A', 'B']], dtype=object)
real = pd.DataFrame([[1.5]], index=[0], columns=['A|B'])

res = helper.shuffled_analysis(10, meta, counts, interactions, combos, {}, real, 1, '|')
print("completed with", len(res), "results")
```

**Expected:** 10 shuffle results. **Got:** `ZeroDivisionError: float modulo`.

The same call reaches the user through `cpdb_statistical_analysis_method.call(...,
iterations=10, threads=1)`; going through the full method only adds a database and a counts file
to the reproduction without changing the traceback.

*What shrinking the example revealed:* the failure is independent of the data, the database and
the number of interactions — the only inputs that matter are `iterations` and `threads`. That
narrowed it to the progress-reporting arithmetic rather than anything in the statistics, and
identified the exact boundary: `iterations = 50` fails, `iterations = 51` works (`round(0.5) = 0`,
`round(0.51) = 1`), and `threads >= 2` is never affected because the pooled branch has no
`progress_step`.

### Suggested fix

`progress_step = max(1, int(round(iterations / 100)))`. No effect on any result — `progress_step`
only drives the progress print. **A patch with a regression test is attached in the PR** (the test
drives `shuffled_analysis` at iterations 1, 10, 50 and 51 on a hand-built four-cell input and
needs no database download, so it runs in CI next to the existing tests; it fails on unpatched
master and passes with the fix).

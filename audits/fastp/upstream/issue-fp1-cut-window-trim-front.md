Title: --cut_front/--cut_tail with --trim_front1/--trim_tail1 removes cut_window_size-1 extra bases (comment on #474)

_This is a **comment for the existing issue [#474](https://github.com/OpenGene/fastp/issues/474)**
("global trimming trims too much when combined with quality pruning for SE data"),
not a new issue: #474 reports exactly this behaviour (`-f 6 -5 -3` removes nine
bases instead of six) and is still open. The text below adds the cause, the 3'
mirror, and the size of the effect. #474 has one comment that I could not read
from this environment -- please read it before posting._

---

Still present on `master` (dce5c40) and in v1.3.6, and in every release I could
build back to v0.20.0. The extra loss is exactly `cut_window_size - 1` bases,
it happens on the 5' side and on the 3' side, and it happens even when every
base of the read is Q40, i.e. when no sliding window can fail.

**fastp version and platform:** master @ dce5c40 and the v1.3.6, v1.0.0,
v0.26.0, v0.23.4, v0.23.2, v0.22.0, v0.20.1 and v0.20.0 release tags, all built
from source with g++ 13.3 on Linux x86-64.

**Command line:** `fastp -i read.fastq -o out.fastq --cut_front -f 5`

**Example input read** (60 nt, every base Q40, so no window can be below the
default `--cut_mean_quality 20`):

```
@r1
ACGTACGTACGTACGTACGTACGTACGTACGTACGTACGTACGTACGTACGTACGTACGT
+
IIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIIII
```

**Output fastp produces:** a 52 nt read (55 nt with `-W 10`: 46 nt).

**Expected output:** a 55 nt read -- `-f 5` removes five bases and `--cut_front`
removes nothing, which is what each option does on its own.

**Minimal complete reproduction** (`mcve_fp1_cut_front_trim_front.py`):

```python
import os, subprocess, sys, tempfile

FASTP = sys.argv[1] if len(sys.argv) > 1 else "fastp"
read = "ACGT" * 15                       # 60 nt
with tempfile.TemporaryDirectory() as tmp:
    path = os.path.join(tmp, "read.fastq")
    with open(path, "w") as f:
        f.write("@r1\n%s\n+\n%s\n" % (read, "I" * 60))
    for label, args in (("--cut_front -f 5", ["--cut_front", "-f", "5"]),
                        ("--cut_tail  -t 5", ["--cut_tail", "-t", "5"]),
                        ("-f 5 (control)  ", ["-f", "5"])):
        out = os.path.join(tmp, "out.fastq")
        subprocess.run([FASTP, "-i", path, "-o", out, "-j", os.path.join(tmp, "j"),
                        "-h", os.path.join(tmp, "h")] + args, capture_output=True)
        seq = open(out).read().splitlines()[1]
        print("%s: output read is %d nt (expected 55)" % (label, len(seq)))
```

```
--cut_front -f 5: output read is 52 nt (expected 55)
--cut_tail  -t 5: output read is 52 nt (expected 55)
-f 5 (control)  : output read is 55 nt (expected 55)
```

**Cause.** In `Filter::trimAndCut` the 5' scan stops on the first window that
passes and then moves the cut position to the end of that window
(`src/filter.cpp:120-122`):

```cpp
        // the trimming in front is forwarded and rlen is recalculated
        if(s >0 )
            s = s+w-1;
```

Moving to `s+w-1` is right when a window failed -- windows overlap, so dropping
the last failing window (which ends at `s+w-2`) means keeping from `s+w-1`. The
guard is there to skip that advance when the very first window already passes,
but it compares `s` with the start of the *untrimmed* read instead of `front`,
the position where the scan started. With `--trim_front1 > 0` the scan starts at
`front > 0`, so the guard is always true and `w-1` good bases are dropped from
every read. `src/filter.cpp:188-190` has the same problem on the 3' side, where
`if(t < l-1)` should be `if(t < l-tail-1)`.

`--cut_right` is not affected (it computes `rlen` only when a window actually
failed), which matches what #474 observed.

**What shrinking the example showed.** The read content does not matter, only
that the first window passes: any all-Q40 read reproduces it, one read is
enough, and the number of lost bases is exactly `cut_window_size - 1` (3 by
default, 9 with `-W 10`), on each side, so `--cut_front --cut_tail -f 5 -t 5`
loses 6. On 20,000 random reads (40-150 nt, Phred 2-40) `--cut_front -f 5`
produced a different read from the corrected rule for 11,509 of them; with the
default filters and `-l 15` that is 1,624 reads lost and 6.9 % of the surviving
bases.

**Proposed fix.** Compare with `front` and `l-tail-1`. A branch with the fix and
two new cases in `Filter::test()` (both fail without it) is ready; PR follows.

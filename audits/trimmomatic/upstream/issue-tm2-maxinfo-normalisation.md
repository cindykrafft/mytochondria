Title: MAXINFO trims every read to one base for targetLength >= 248 (strictness 0.1), >= 495 (0.2) or >= 711 (any strictness): the long score tables overflow

<!-- usadellab/Trimmomatic has no issue template; sections follow the README's own order: what was run, what happened, what was expected. -->

**Version:** `main` @ ef98d62 (0.41), and every release run: 0.41, 0.40, 0.39 (release jars), 0.38, 0.36, 0.33, 0.32 (built from the tags). Java 25.0.4, Ubuntu 24.04.

**What happened**

`MAXINFO:250:0.1` on a 300-nt read whose every base is Q40 keeps one base. `MAXINFO:247:0.1` keeps all 300. The same happens for any strictness once `targetLength` reaches 711, and for strictness 0.2 from 495 on. After `MINLEN` such a run drops every read.

**Minimal example** (`mcve_tm2_maxinfo_target_length.py <trimmomatic.jar>`):

```python
#!/usr/bin/env python3
import os, subprocess, sys, tempfile
jar = sys.argv[1]
d = tempfile.mkdtemp()
open(os.path.join(d, "in.fq"), "w").write("@r\n%s\n+\n%s\n" % ("ACGT" * 75, "I" * 300))   # one 300-nt read, all Q40
for step in ("MAXINFO:247:0.1", "MAXINFO:248:0.1", "MAXINFO:250:0.1", "MAXINFO:800:0.5"):
    out = os.path.join(d, "out.fq")
    subprocess.run(["java", "-jar", jar, "SE", "-threads", "1", "-phred33", os.path.join(d, "in.fq"), out, step], capture_output=True)
    print("%-16s expected 300 bases kept, got %d" % (step, len(open(out).read().split("\n")[1])))
```

Output on `main` (ef98d62), 0.41 and 0.39:

```
MAXINFO:247:0.1  expected 300 bases kept, got 300
MAXINFO:248:0.1  expected 300 bases kept, got 1
MAXINFO:250:0.1  expected 300 bases kept, got 1
MAXINFO:800:0.5  expected 300 bases kept, got 1
```

Shrinking showed that the read does not matter (any length, any quality gives 1 base); only the `targetLength`/`strictness` pair does, and the boundary is where the arithmetic below overflows.

**Why** (`MaximumInformationTrimmer.java`): the two log-score tables are scaled to `long` with a single ratio, `normRatio = Math.max(calcNormalization(lengthScoreTmp, ...), calcNormalization(qualProbTmp, ...))` (`:67-68`). `Math.max` picks the larger ratio, i.e. the one computed for the table with the smaller maximum (the quality table, |max| ≈ 1.23·strictness), and applies it to the length table too, whose first entries are ≈ −(targetLength − 1). Once `(targetLength − 1) · Long.MAX_VALUE / (2000 · 1.23 · strictness)` exceeds `Long.MAX_VALUE`, the cast `(long) (array[i] * ratio)` (`:34`) saturates at `Long.MIN_VALUE`, and `ls + accumQuality` (`:94`) wraps to a large positive number at position 0, which becomes `maxScore`; every later position scores lower, so `maxScorePosition` stays 1. That gives the boundaries 248 (strictness 0.1) and 495 (0.2). From `targetLength` 711 on, `Math.exp(parLength - i - 1)` (`:48`) is `Infinity` for the first positions, `Math.log(1/(1+Infinity))` is `-Infinity`, and the same saturation follows at any strictness. (`calcNormalization` also seeds `maxVal` with `array[0]` rather than `Math.abs(array[0])`, `:19`, which is why the quality table's maximum is the second entry.)

A double-precision evaluation of the same formula keeps all 300 bases in every cell of a 25 × 6 grid of (targetLength, strictness); the shipped build differs in 41 cells, all in the region above. At the settings people use (targetLength 35–150, strictness 0.2–1.0) the shipped result equals the double-precision rule for 5,000 of 5,000 reads with realistic qualities under each of seven settings, so the fix changes nothing there.

**Fix**: use `Math.min` for `normRatio` (the smaller ratio is the one that keeps *both* tables inside `long` range: the quality sum over 1,000 bases then stays below `Long.MAX_VALUE / 2`), take `Math.abs(array[0])` in `calcNormalization`, and evaluate `log(1/(1+e^x))` as `-x` when `x > 700`. A branch with the fix and a regression test (`MaximumInformationTrimmerLargeTargetTest`, three of its four tests fail on unmodified `main`; full suite 259 → 263 tests passing) is ready; PR follows.

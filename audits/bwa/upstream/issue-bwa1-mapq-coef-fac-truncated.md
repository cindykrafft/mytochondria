Title: bwa mem MAPQ: mapQ_coef_fac is declared int, so ln(50) is truncated to 3 and MAPQ drops by ~40% at 50 bp

<!-- lh3/bwa has no issue template. First filing. Every release since 0.7.6. -->

**Versions:** 0.7.12, 0.7.15, 0.7.17 and 0.7.19 / `master` @ d82444c, same behaviour (the code dates from r418, 2013-11-02).

`mem_opt_init()` sets `o->mapQ_coef_len = 50; o->mapQ_coef_fac = log(o->mapQ_coef_len);` (and `-Q` does the same in `fastmap.c`), but `mem_opt_t` declares

```c
float mapQ_coef_len;
int mapQ_coef_fac;
```

so ln 50 = 3.912 is stored as 3. In `mem_approx_mapq_se()`

```c
tmp = l < opt->mapQ_coef_len? 1. : opt->mapQ_coef_fac / log(l);
tmp *= identity * identity;
mapq = (int)(6.02 * (a->score - sub) / opt->a * tmp * tmp + .499);
```

the length factor is then 1 for l < 50 and 3/ln(l) for l ≥ 50: it drops from 1 to 0.767 at l = 50 instead of continuing smoothly as ln(50)/ln(l), and it enters squared, so every MAPQ below the cap for an alignment of 50 bp or longer is about 41% lower than the formula intends. This includes both mates of a pair before the pairing adjustment.

**Reproduction:** a 100-kb random reference in which a 400-bp segment is copied once with a single base changed; reads of 40-60 bp centred on that base, taken from the first copy (so AS = L and XS = L − 5 for every length). `bwa mem` with default options:

```
   L   AS   XS   MAPQ (0.7.19)   MAPQ with mapQ_coef_fac as float
  45   45   40     27               27
  48   48   43     27               27
  49   49   44     27               27
  50   50   45     15               27
  51   51   46     15               27
  52   52   47     14               27
  55   55   50     14               26
  60   60   55     13               24
```

A port of `mem_approx_mapq_se()` reproduces all 158 single-end MAPQs in a wider test (unique and two-/three-copy reads, 50-150 bp, 0-8 mismatches) on 0.7.12, 0.7.15, 0.7.17 and 0.7.19 when the factor is 3, and only 120 of them when it is ln 50. Examples from that set: 100-bp read with AS 100 / XS 85 gets MAPQ 38 (60 with the float factor); 150 bp, AS 135 / XS 120 gets 30 (51); 70 bp, AS 70 / XS 60 gets 30 (51).

I also checked whether the truncated value happens to calibrate better. On simulated reads from a 3-Mb genome with 33% planted repeats (300-3,000 bp, 2-20 copies, 0.5-15% divergence), both builds are conservative, and the float factor moves MAPQ closer to its Phred meaning without adding errors at the usual filters. For single-end 150-bp reads, MAPQ 1-59 had 12 wrong placements where the MAPQs promise 1,089 (released) and 23 where they promise 292 (float). The float factor also brings 2,190 more reads to MAPQ ≥ 30 (51,892 → 54,082), all of them correctly placed. At 100 bp the gain is 1,939 reads, all correct. Pairs barely change (58,016 → 58,017 at MAPQ ≥ 30). This is a simulation, not the human genome.

**Fix:** declare the field `float`. `mem_opt_t` keeps its size and layout, since `int` and `float` are both 4 bytes. With the change, only column 5 differs; every other SAM field is identical on the reads above. I have the one-line patch ready if you want it. I realise this changes MAPQ for every BWA-MEM user, and BWA-MEM2 has the same `int` declaration (`src/bwamem.h`), so the two would no longer match. If you would rather keep the legacy output frozen, a sentence in the man page saying the factor is 3/ln(l) above 50 bp would let people interpret it.

Title: CollectHsMetrics ZERO_CVG_TARGETS_PCT divides the count of unique zero-coverage targets by the raw number of intervals in the file (regression since 2.19.0)

<!-- broadinstitute/picard .github/ISSUE_TEMPLATE.md, Bug Report block -->

## Bug Report

### Affected tool(s)
CollectHsMetrics, CollectTargetedPcrMetrics (`TargetMetricsCollector`): `ZERO_CVG_TARGETS_PCT`.

### Affected version(s)
- [x] Latest public release version [3.3.0; also 3.0.0 and 2.27.4. 2.18.7 is correct.]
- [x] Latest development/master branch as of [2026-09-24, c2a483d]

### Description

`TargetMetricsCollector.calculateTargetCoverageMetrics` counts the targets without coverage by iterating over `highQualityCoverageByTarget`, whose keys are the **uniqued** target intervals (overlapping and duplicate intervals merged), and then divides by the number of intervals **as given in the file**:

```java
metrics.ZERO_CVG_TARGETS_PCT = zeroCoverageTargets / (double) allTargets.getIntervals().size();
```

Until Picard 2.18.x the two counts agreed because htsjdk's `IntervalList.fromFiles()` returned the union of the input lists. htsjdk 2.19.0 changed `fromFiles()` to a plain concatenation (samtools/htsjdk#1273, "Changed IntervalList fromFiles() so that it doesn't call .unique()"), and Picard 2.19.0 picked that up, so since then a target file with overlapping intervals — common in vendor designs that list the exons of overlapping transcripts separately — understates the fraction of targets without coverage by the overlap factor. `TARGET_TERRITORY` and the `PCT_TARGET_BASES_xX` metrics use the unique territory and are right; only this fraction mixes the two.

#### Steps to reproduce

Eight target intervals of which two pairs overlap (six unique targets after merging); reads cover the two merged targets only, so four of the six unique targets have no coverage:

```sh
cat > targets.interval_list <<'EOF'
@HD	VN:1.6	SO:coordinate
@SQ	SN:chr1	LN:5000
chr1	100	200	+	A1
chr1	150	250	+	A2
chr1	400	500	+	B1
chr1	450	550	+	B2
chr1	700	800	+	C
chr1	900	1000	+	D
chr1	1200	1300	+	E
chr1	1500	1600	+	F
EOF
A=$(printf 'A%.0s' $(seq 100)); Q=$(printf 'I%.0s' $(seq 100))
{ printf '@HD\tVN:1.4\tSO:coordinate\n@SQ\tSN:chr1\tLN:5000\n@RG\tID:rg1\tSM:s1\tLB:l1\tPL:ILLUMINA\n'
  for i in $(seq 0 9); do printf 'a%d\t0\tchr1\t100\t60\t100M\t*\t0\t0\t%s\t%s\tRG:Z:rg1\nb%d\t0\tchr1\t400\t60\t100M\t*\t0\t0\t%s\t%s\tRG:Z:rg1\n' $i "$A" "$Q" $i "$A" "$Q"; done; } > reads.sam
java -jar picard.jar CollectHsMetrics -I reads.sam -O hs.txt --BAIT_INTERVALS targets.interval_list --TARGET_INTERVALS targets.interval_list
grep -A2 "^## METRICS" hs.txt | cut -f 26        # ZERO_CVG_TARGETS_PCT (column of TARGET_TERRITORY is 4)
```

(`h1_hsmetrics_zero_cvg_targets.py` in the linked repository is the same reproduction with pysam-built input, run on 2.18.7, 2.27.4, 3.0.0, 3.3.0 and master.)

#### Expected behavior

`ZERO_CVG_TARGETS_PCT` = 4 / 6 = 0.666667 ("the fraction of targets that did not reach coverage=1 over any base"), and it is on 2.18.7.

#### Actual behavior

```
ZERO_CVG_TARGETS_PCT 0.5        (4 unique uncovered targets / 8 intervals in the file)
TARGET_TERRITORY     706        (unique bases: correct)
```

on 2.27.4, 3.0.0, 3.3.0 and master.

**Fix:** divide by `highQualityCoverageByTarget.size()`, the set the numerator is counted over. A PR with that change and a regression test (the input above, which fails on `master`) follows.

### PR 1 — `fix/rnaseq-coverage-last-base` — "CollectRnaSeqMetrics: count the last base of each alignment block in transcript coverage"

### Description

Fixes #NNN.

`Gene.Transcript.addCoverageCounts()` looped over `genomeStart <= i < genomeEnd`, but its only
caller, `RnaSeqMetricsCollector`, passes `CoordMath.getEnd(blockStart, blockLength)`, the inclusive
last reference base of the alignment block. The last aligned base of every block was therefore
never added to the per-transcript coverage that feeds `MEDIAN_CV_COVERAGE`, `MEDIAN_5PRIME_BIAS`,
`MEDIAN_3PRIME_BIAS`, `MEDIAN_5PRIME_TO_3PRIME_BIAS` and the `normalized_coverage` histogram. For a
spliced read the block ends at the exon end, so the last base of every internal exon only got
coverage from reads running unspliced into the intron.

This makes the loop inclusive (`i <= genomeEnd`) and documents the contract on the method. On a
transcript covered uniformly by 50 reads at every base the tool now reports `MEDIAN_CV_COVERAGE`
0 and normalized coverage 1.0 everywhere (before: 0.032 and 0.91 at the junction); on a 276-gene
synthetic library `MEDIAN_CV_COVERAGE` moves from 0.436 to 0.430 and the last point of the
coverage curve from 0.053 to 0.058, matching an independent per-base count to six digits. No
other metric changes; the base-classification counts use a separate loop.

Test: `CollectRnaSeqMetricsTest.testCoverageIncludesLastBaseOfEachAlignmentBlock` builds the
two-exon transcript with `SAMRecordSetBuilder` and asserts CV 0, biases 1 and a flat histogram; it
fails on `master`.

### PR 2 — `fix/hsmetrics-zero-cvg-denominator` — "CollectHsMetrics: divide ZERO_CVG_TARGETS_PCT by the number of unique targets"

### Description

Fixes #NNN.

`TargetMetricsCollector` counts the targets without coverage over the uniqued target list
(overlapping and duplicate intervals merged) but divided by `allTargets.getIntervals().size()`, the
number of intervals in the file as given. Until htsjdk 2.19.0 `IntervalList.fromFiles()` returned
the union of the input lists, so the two counts agreed; since Picard 2.19.0 (htsjdk 2.19.0,
samtools/htsjdk#1273) `fromFiles()` concatenates and the denominator is the raw interval count, so
target files with overlapping intervals understate the fraction of targets without coverage.

This divides by `highQualityCoverageByTarget.size()`, the set the numerator is counted over, and
says so in a comment. No other metric changes (`TARGET_TERRITORY` and `PCT_TARGET_BASES_xX` already
use the unique territory).

Test: `CollectHsMetricsTest.testZeroCvgTargetsPctCountsUniqueTargets` (8 intervals merging to 6
unique targets, 4 uncovered) asserts 4/6; it fails on `master` (0.5).

### PR 3 — `fix/alignment-summary-bisulfite-ref-index` — "CollectAlignmentSummaryMetrics: compare bisulfite bases against the aligned reference base"

### Description

Fixes #NNN.

With `IS_BISULFITE_SEQUENCED=true`, `AlignmentSummaryMetricsCollector.collectQualityData()` called
`SequenceUtil.bisulfiteBasesEqual()` with `refBases[readBaseIndex]`, the reference base at the read's
offset from the start of the contig, instead of `refBases[refIndex + i]`, the base the read base is
aligned to (which the mismatch test on the previous line already uses). A converted base was
therefore excused only when the contig's base at that offset happened to be a C (or a G on the
reverse strand), so `PF_MISMATCH_RATE` and `PF_HQ_ERROR_RATE` for bisulfite data depended on the
first read-length bases of each contig rather than on the alignment, and a read with a leading
soft clip aligned to a contig shorter than the read raised `ArrayIndexOutOfBoundsException`.

This uses the aligned reference position. Non-bisulfite runs are unchanged.

Test: `CollectAlignmentSummaryMetricsTest.testBisulfiteMismatchesUseTheAlignedReferenceBase` with
two new small test-data files (a contig starting with 100 A's, one forward read with every C->T and
one reverse read with every G->A, and a `40S60M` read on a 60-bp contig) asserts a mismatch rate of
0; it fails on `master` with the exception.

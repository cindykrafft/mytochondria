To put numbers on the off-by-one you both identified: `GcBiasUtils.calculateAllGcs` fills `gc[i]` for 0-based window starts `1 <= i < lastWindowStart` and leaves `gc[0]` and `gc[lastWindowStart..refLength]` at their default 0, while `GcBiasMetricsCollector.addRead` looks up `gc[pos]` with `pos = rec.getAlignmentStart()` (1-based) for forward reads and `alignmentEnd - windowSize` for reverse reads, accepting any value `>= 0`. Two consequences, both reproducible on 2.18.7 through the current master with a two-contig reference:

1. A forward read starting at base 1 of a contig whose bases 1-100 are A and base 101 is G is binned at **GC 1**; the documented window (the 100 bases from the read's 5' end) has GC 0. Reverse reads are exact (their window is `[end-100+1, end]`), so the two strands are binned against windows offset by one base.
2. On a 300-bp contig with a 100-bp forward read at every start position, the 101 reads starting at 1-based 200-300, whose window does not fit in the contig, are all counted in the **GC = 0** bin (`READ_STARTS` 101 at GC 0, 199 at GC 50), and `calculateRefWindowsByGc` skips the first and last windows of every contig as you said. Reads whose window runs off the end should be dropped, as reads in windows with more than four N's are.

For whole chromosomes the second point is a 10^-6 effect; for fragmented assemblies, transcriptome references and amplicon panels every contig contributes its end reads to the GC-0 bin and to `AT_DROPOUT`. The stand-alone reproduction (`g1_gcbias_window.py`) and its output on five versions are in the repository linked below. A fix is to index `gc` with `pos - 1` for forward reads and treat `pos > lastWindowStart` as "no window" (return -1 or skip), which also makes `calculateRefWindowsByGc` cover the first window; I can send a PR if that shape is acceptable.

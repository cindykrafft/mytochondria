### PR 1 — `fix/splitonly-singleton-fragments` — "featureCounts: apply --splitOnly to singleton fragments in read-pair mode"

Closes #NNN.

With `-p --countReadPairs --splitOnly`, a fragment is excluded only after two mapped non-split records have been seen (`skipped_for_exonic == 1 + is_paired_end_mode_assign`). An unmapped mate leaves the record loop at the `SAM_FLAG_UNMAPPED` `continue` before that test, and a single-end record in a paired-end file gets an unmapped placeholder mate, so every non-split fragment with exactly one mapped record is counted as if it were split. The users guide says only alignments whose CIGAR contains `N` are counted with this option.

This change counts an unmapped record as a non-split record in read-pair mode, so a fragment is excluded when none of its mapped records is split, and moves the `Unassigned_NonSplit`/`Unassigned_Split` bookkeeping (details file, read-group counters, scRNA pool) into one helper used by both branches. `--nonSplitOnly` and read-level counting are unchanged.

Test: `test/featureCounts/data/corner-SPLITONLY.{sam,ora}` and one line in `test_corner_cases.sh` — three non-split singleton fragments, two single-end non-split records, two non-split pairs, two split pairs and one split singleton; expected `simu_gene1 = 3`. Unmodified code gives 8 and `compare.sh` prints FAILED; with the change the whole `featureCounts-test.sh` suite passes. On a 1,000-singleton file the count for the gene goes from 1,000 to 0; a 75-option-set random battery against an independent implementation of the manual is otherwise unchanged.

### PR 2 — `fix/read-type-filter` — "featureCounts: restore the read-type filter for stranded counting"

Closes #NNN. (Open only after the maintainers confirm on the issue that the manual, not the 2.0.2 code, is the intended behaviour.)

The users guide ("Read filtering", "Program output") says single-end reads found in a paired-end library are excluded from strand-specific counting as `Unassigned_Read_Type`, because their strand cannot be related to the strand of the fragment. Release 2.0.1 did this; the 2.0.2 changes (`1f24de1`) removed the branch while keeping the counter and the summary row, so since then such reads are counted as first reads — an orphaned second read is compared with the wrong strand and, under `-s 2`, lands on the antisense gene.

This change restores the exclusion where the inconsistent read type is detected, with the counter routed through the read-group tables and the scRNA pool like the neighbouring filters. It applies whenever `-p` is given with `-s 1` or `-s 2` (fragment counting and read-level counting of a paired-end library); `-s 0` and `-B` are unchanged.

Test: `test/featureCounts/data/corner-READTYPE.{sam,ora}` — four proper pairs from the `+` gene and four single-end records inside it, counted with `-p --countReadPairs -s 1`; expected `simu_gene1 = 4`. Unmodified code gives 6 (the two forward single-end reads) and FAILED; with the change the whole suite passes. On a 300-pair / 1,000-orphan dUTP file the counts return from S = 800, AS = 500 to S = 300, AS = 0, which is what 2.0.1 gives.

Title: voom() with a DGEList offset matrix counts the library sizes twice; voomLmFit() in devel reads the same offset as exp(offset)

<!-- Bioconductor support site post (https://support.bioconductor.org, tag: limma). Post after LI1

     (devel; applies on top of the LI1 devel patch). -->

Since limma 3.68.0 `voom()` picks up the `offset` element of a DGEList, row-mean corrects it
and adds it to `log(lib.size)` (`R/voom.R:55-67`; the help page says an edgeR-style offset
"will be row-mean corrected and treated as a prior offset matrix"). An edgeR offset already
contains the log library sizes — `scaleOffset()` puts it on the scale of `log(lib.size)`,
and `glmFit()`/`cpm()` use `exp(offset)` in place of the library sizes — so row-centring it
removes the gene means but not the column `log(lib.size)`, and the effective library size
`voom()` uses is `lib.size^2/geomean(lib.size)` (times the gene-specific part). The devel
`voomLmFit()` now reads the same slot the edgeR way ("the library sizes will be set to
`exp(offset)`", NEWS 4.0.0), so `voom()` and `voomLmFit()` disagree on the same object.

**Minimal example** (limma 3.68.5 with edgeR 4.0.16, R 4.3.3; identical on 3.68.4 and devel
3.99.0; `edgeR::voomLmFit` 4.10.5 does the same):

```r
library(limma); library(edgeR)
set.seed(81)
counts <- matrix(rnbinom(6*4, mu=100, size=10), 6, 4)
lib <- c(1e6, 4e6, 2e6, 8e6)
y <- DGEList(counts, lib.size=lib)
y$offset <- matrix(log(lib), 6, 4, byrow=TRUE)      # the trivial edgeR offset: log library sizes, as scaleOffset(y, 0) stores
voom(y)$E - voom(counts, lib.size=lib)$E             # every row:
#>   Sample1 Sample2 Sample3 Sample4
#> 1     1.5    -0.5     0.5    -1.5                  # = -log2(lib/geomean(lib))
-log2(lib/exp(mean(log(lib))))
#> [1]  1.5 -0.5  0.5 -1.5
```

**Expected:** an offset equal to `log(lib.size)` is a no-op, so the difference is 0 (as it is
for `voomLmFit()` in devel, 8.9e-16, and for `voom(counts, lib.size=lib, offset.prior=0)`).
**Got:** `E` shifted by −log2(lib.size/geomean) per column; the library sizes voom actually
used, recovered from `E`, are `lib.size` times 0.354, 1.414, 0.707, 2.828 = lib.size/geomean.

**Effect downstream:** with 6,000 simulated genes and group 2 sequenced 2.5× deeper (an
offset carrying only the column sums), every group logFC is shifted by −1.507 (the log2
ratio of the groups' library sizes is 1.512) and 5,374 genes are called at adj.P < 0.05, all
"down", against 37 in the run with `lib.size` (500 true). With a cqn-style offset
`log(lib.size) + d` the returned `E` equals `log2((counts+0.5)/(lib.size^2/geomean * exp(d) + 1)*1e6)`
to 5e-15; supplying the same `d` as `offset.prior` gives the edgeR reading exactly.

Shrinking the example showed what it needs: a DGEList with an `offset` element (or the
`offset=` argument) whose columns differ in mean, i.e. any offset on edgeR's scale; when all
library sizes are equal the double count cancels.

**Proposal** (patch against devel attached; it applies on top of the arrayWeights patch):
make `voom()` give `offset` precedence over `lib.size` and `offset.prior` and set the library
sizes to `exp(offset)`, exactly as `voomLmFit()` does, accept a vector offset, keep
`offset.prior` unchanged, update the help page and add `tests/voom-offset.R` (fails on the
unmodified code). This changes results only for DGELists carrying an `offset` element, which
is why it is offered as a question rather than a bug report: if the row-centred reading is
intended, the help pages of `voom()` and `voomLmFit()` describe opposite conventions for the
same slot and edgeR users of cqn/EDASeq offsets get library sizes squared in `voom()`.

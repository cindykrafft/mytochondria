Fixes #1423.

This is the `deeptoolsintervals/parse.py#L15` pattern you pointed at in the issue thread — the same `if not isinstance(line, str): line = line.decode('ascii')` guard that `getNext()` uses there and that `loadGTF()` already has a few lines further down in this file — applied to `loadBED()`. Rebased onto the 4.0.0 tree: the Rust-backed `computeMatrix` now reads gzipped BED files itself (the `test_computeMatrix_referencepoint.py` gz cases cover that), so the `computeMatrix` half of #1423 is already closed; what is left is `computeMatrixOperations sort -R regions.bed.gz` (and `computeMatrix_old`), which still goes through `loadBED()` and still fails with the reported `TypeError`.

**Cause.** `sortMatrix()` opens the regions file with `deeptoolsintervals.openPossiblyCompressed()`, which returns a binary handle for a gzipped file; `getNext()` decodes the header/first line, but `loadBED()` then iterates the remaining lines of the handle as `bytes`, so `line.startswith("#")` raises `TypeError: startswith first arg must be bytes or a tuple of bytes, not str`. `loadGTF()` in the same file already decodes its lines.

**Fix.** Decode non-`str` lines in `loadBED()` exactly as `loadGTF()` does (two lines in `pydeeptools/deeptools/computeMatrixOperations.py`). No change for plain-text BED files.

**Test.** `test_computeMatrixOperations.py::testsortGzippedBED` runs `computeMatrixOperations sort` on a gzipped copy of the existing `computeMatrixOperations.bed` and checks the same md5 as the existing `testsort`. It fails on `master` (`4db9d816`) with the `TypeError` above and passes with the fix.

**Run.** `pytest pydeeptools/deeptools/test/test_computeMatrixOperations.py`: 7 passed + 1 failed (the new test) before, 8 passed after; full suite 233 passed with the fix (232 on unmodified `master`, no failures). A `CHANGES.txt` bullet is included in the 4.0.0 section.

One thing I noticed while reproducing, not touched here: the Rust `computeMatrix` labels a single region file's group by the file stem (`regions` for `regions.bed`), while `computeMatrixOperations sort` with one `-R` file expects the group to be called `genes` (`sortMatrix`, `defaultGroup = "genes"`), so sorting a single-BED 4.0.0 matrix only works if the BED is named `genes.bed`. `computeMatrix_old` still labels it `genes`.

### Cause

Since the transformer refactor (#2536), `Neighbors.compute_neighbors` only restricts `.distances` to the `n_neighbors - 1` nearest neighbors on the brute-force shortcut path (`transformer="sklearn"`, or the default below 8192 cells with the euclidean metric). For every other transformer the raw `fit_transform` output is stored as is. `PyNNDescentTransformer` returns `n_neighbors` neighbors *plus* the cell itself, so with `transformer="pynndescent"` — and with the default `transformer=None` on ≥ 8192 cells — `.obsp["distances"]` holds `n_neighbors` non-zero entries per row instead of the documented `n_neighbors - 1`, while `.obsp["connectivities"]` is built from the truncated `n_neighbors - 1` neighbors. On a 8,500-cell random matrix with `n_neighbors=15`, 384 of the first 500 cells have a neighbor in `distances` that is not an edge in `connectivities`. Scanpy 1.9 built `distances` from the truncated kNN arrays on this path, so this is a regression from 1.10.

### Fix

Rebuild `.distances` from the truncated `knn_indices`/`knn_distances` (`keep_self=False`) for every transformer when `knn=True`, exactly as the shortcut path already did. The brute-force path is unchanged; `distances` for the pynndescent and custom-transformer paths now has `n_neighbors - 1` entries per row and the same sparsity pattern the connectivities use.

### Tests

- New `test_distances_n_neighbors` (pynndescent and a `KNeighborsTransformer` instance): asserts `n_neighbors - 1` stored and non-zero entries per row and that every `distances` edge is a `connectivities` edge. Fails on `main` (`6` stored entries per row where `4` are expected), passes with the fix.
- `test_distances_all`: the `pynndescent` and `sklearn`-instance cases now expect the kNN distances (`distances_euclidean`) rather than all pairwise distances, matching the `knn=True` shortcut path in `test_distances_euclidean`.

- `ruff check` and `ruff format --check` pass on the changed files.

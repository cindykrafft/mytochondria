Following up on @flying-sheep's "we should definitely bring this in line": I traced where the extra neighbour comes from on `main` (`fc4dbec`; the neighbors code is unchanged since `ec374022`, where I first ran it). `Neighbors.compute_neighbors` truncates `.distances` to the `n_neighbors - 1` nearest neighbours only on the brute-force shortcut path; for every other transformer it stores the raw `fit_transform` output, and `PyNNDescentTransformer` returns `n_neighbors` neighbours plus the cell itself. That includes the default `transformer=None` once `n_obs >= 8192`, since that switches to pynndescent. The connectivities are built from the truncated arrays, so `.obsp["distances"]` carries one neighbour per cell that `.obsp["connectivities"]` never uses (384 of 500 checked cells on a random 8,500-cell matrix). Scanpy 1.9 built `distances` from the truncated kNN arrays on this path, so this came in with the transformer refactor (#2536).

A side effect: `method="gauss"` on that path weighted all `k` stored neighbours and gave every cell a self-loop of weight 1.0 (from the stored self-distance of 0). `umap` connectivities already used the truncated arrays and do not change.

Title: Per sequence GC content uses only the first 100 bases of a 101–199-bp read, while the documentation says the whole length of each sequence

<!-- s-andrews/FastQC has no issue template. Third filing (report: page or code, the maintainer's call). Every version. Send after FQ1 or FQ2 has a reply. -->

**Versions:** 0.11.5, 0.11.9, 0.12.1 and `master` @ 87fb336.

`PerSequenceGCContent.truncateSequence` cuts each read to the largest multiple of 100 below its length (a multiple of 1,000 beyond 1,000 bp) before counting G and C, presumably to bound the number of cached `GCModel` objects. For 150-bp reads a third of every read is ignored, for 250-bp reads a fifth. The module page says the module "measures the GC content across the whole length of each sequence", and `%GC` in Basic Statistics counts every base, so the two numbers describe different things without saying so.

**Reproduction:** 4,000 reads of 150 bp whose first 100 bases have GC drawn from N(45 %, 6 %) and whose last 50 bases are G (the two-colour poly-G artefact):

```
true whole-read GC (mean)            63.3 %
GC of the first 100 bases (mean)     44.9 %
Per sequence GC content, mean        45.4 %      (distribution identical to a port that truncates to 100 bases)
Basic Statistics %GC                 63
```

On 100-bp reads the distribution equals a port with no truncation exactly. Script: `f2_gc_duplication.py` in the repository linked below.

Either the page should say that reads longer than 100 bp are truncated to a multiple of 100 (and Basic Statistics' `%GC` is not), or the truncation should go: a `GCModel` for one length is 101 small arrays, and libraries rarely contain more than a few hundred distinct lengths, so caching one model per observed length is cheap. I can send a PR for whichever you prefer.

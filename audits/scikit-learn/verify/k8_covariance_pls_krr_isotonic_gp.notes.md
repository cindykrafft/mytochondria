## FAIL lines

### 1. `OAS: omitting the 2/p terms of Chen et al. Eq. 23 'doesn't affect the value of the estimator' (docstring)` — all builds

Measured: on 20 x 4 correlated integer data the shrinkage computed with the exact rational arithmetic of scikit-learn's own formula (`num = tr(S^2) + tr(S)^2`, `den = (n+1)(tr(S^2) - tr(S)^2/p)`) is 0.20061 and the library returns exactly that (rel. dev < 1e-12, the OAS closed form itself holds); the paper's Eq. 23, which multiplies `tr(S^2)` by `(1 - 2/p)` and uses `(n + 1 - 2/p)` in the denominator, gives 0.16544 — a difference of 0.035, 21 % relative. The added table (`OAS with n=60, p=...` lines) shows the relative difference is 11 % at p = 4, 2 % at p = 10, 0.1 % at p = 50 and 0.0 % at p = 200. Library: `covariance/_shrunk_covariance.py::_oas`, comment line 81 "The factor 2 / p is omitted since it does not impact the value of the estimator for large p", and the docstrings of `oas` / `OAS` (lines 686, 785): "In the original article, formula (23) states that 2/p ... is multiplied by Trace(cov*cov) in both the numerator and denominator, but this operation is omitted because for a large p, the value of 2/p is so small that it doesn't affect the value of the estimator." Verdict: documented deviation, but the justification is only true for large p; for the small-p regime the estimator differs from the cited Eq. 23 by tens of percent, so this is a documentation gap (the docstring should say the implemented formula is the large-p approximation and quantify the effect), not a numerical bug. All builds behave identically.

### 3. `MinCovDet 1-D: raw_location_ = mean of raw support ('raw robust estimated location')` — all builds

Measured: 33 one-dimensional points (30 N(0,1) + 3 outliers), h = ceil((n + 2)/2) = 18. Brute force over all contiguous windows of 18 sorted points gives a minimum variance of 0.14439 (1.9.1 data stream; 0.08390 on the 1.1.3/1.2.2 stream, whose RandomState differs after an earlier version-guarded draw), while `raw_covariance_` is 0.15488 (0.09630), 7–15 % larger. `raw_location_` (0.2333) is not the mean of `raw_support_` (0.2515): the two checks that pass show the support does have h points and `raw_covariance_` is the variance of that support, so the discrepancy is in which subset is chosen. Library: `covariance/_robust_covariance.py::fast_mcd`, the "1-dimensional case quick computation" branch (lines 480–497): it finds the *shortest half* (`diff = X_sorted[n_support:] - X_sorted[:n_samples - n_support]`, `halves_start = where(diff == min(diff))`), takes the midpoint of that half as the location (`location = 0.5 * (X_sorted[n_support + halves_start] + X_sorted[halves_start]).mean()`), builds the support as the h points closest to that midpoint (`support[np.argsort(np.abs(X_centered), 0)[:n_support]] = True`) and sets `covariance = [[np.var(X[support])]]`. The shortest half minimises the range (the LMS/LTS location of Rousseeuw & Leroy ch. 4), not the variance, and the MCD subset in 1-D is the contiguous window with minimal variance; the two are different subsets in general, as measured. Documentation: the class is "Minimum Covariance Determinant (MCD): robust estimator of covariance", `raw_covariance_` is "The raw robust estimated covariance before correction and re-weighting", `raw_location_` "The raw robust estimated location before correction and re-weighting"; nothing says the 1-D case is a different estimator. For p >= 2 the p = 2, n = 14 brute force over all 2002 subsets confirms FastMCD returns the true MCD subset with `raw_location_` = support mean. Verdict: bug (or at least an undocumented estimator switch) in the 1-D branch — the returned raw estimates are not the MCD, and location and covariance are computed around different centres. The subsequent correction and reweighting pipeline is applied to these raw values (the pipeline checks pass). Present in all builds, unchanged by the 1.8 consistency-factor rewrite.

### 4/5. `MinCovDet support_fraction=None|0.75: correct_covariance(X) called after fit leaves dist_ unchanged` — all builds

Measured: after `fit`, calling the public `correct_covariance(X)` returns `raw_covariance_` times a factor computed from the *current* (already reweighted) `support_`/`dist_` (that companion check passes: factor 1.4707 for 1.9.1 = Croux/Pison factor at alpha = support_.sum()/n, 1.2659 for < 1.8 = median(dist_)/chi2.isf(0.5, p)), and it divides `self.dist_` in place by that factor (`dist_` changed by 1.47x / 1.27x). Library: `covariance/_robust_covariance.py::MinCovDet.correct_covariance` (line 824ff): `consistency_factor = _consistency_factor(n_features, n_support / n_samples)` where `n_support = np.sum(self.support_)`; `covariance_corrected = self.raw_covariance_ * consistency_factor`; `self.dist_ /= consistency_factor` (line 860); the < 1.8 releases do the same with `correction = np.median(self.dist_) / chi2(p).isf(0.5)`. Documentation: "Apply a correction to raw Minimum Covariance Determinant estimates. ... Returns covariance_corrected: Corrected robust covariance estimate." The docstring documents neither that the factor depends on the current fitted state (so a second call gives a different answer from the one used inside `fit`) nor that `dist_` is mutated. Verdict: documentation gap / API hazard (the method is designed as an internal step of `fit` but is public); `covariance_`, `location_`, `support_`, `dist_` produced by `fit` are all verified correct against my mpmath re-implementation of the pipeline. All builds.

### 6/7/8. `PLSRegression K=1,2,3: documented formula 'y = X @ coef_.T + intercept_' reproduces predict(X) on data with non-zero feature means` — all builds (label reads `Y = X @ coef_ + intercept_` on 1.1.3/1.2.2 and `Y = X @ coef_.T + intercept_` on 1.3.2)

Measured: with feature means (10, -3, 0, 5) the documented linear formula deviates from `predict(X)` by 30–43 % of the prediction range; `predict(X) == (X - x_mean) @ coef_.T + intercept_` with `intercept_ == y.mean(0)` holds to 1e-10 (1.5+), `predict(X) == ((X - x_mean)/x_std) @ coef_.T + intercept_` on 1.3–1.4 and `((X - x_mean)/x_std) @ coef_ + intercept_` on < 1.3 (all verified; coef_ itself matches the NIPALS reference in each version's convention). Library: `cross_decomposition/_pls.py::_PLS.fit` line 364 `self.intercept_ = self._y_mean`; `predict` lines 476–477: `X -= self._x_mean; y_pred = X @ self.coef_.T + self.intercept_` (1.3.2 additionally `X /= self._x_std`; 1.1.3/1.2.2 the same with `_coef_.T`). Documentation (lines 572–576, 722–726, 847–851 for PLSRegression / PLSCanonical / CCA): "coef_: The coefficients of the linear model such that `y` is approximated as `y = X @ coef_.T + intercept_`. intercept_: The intercepts of the linear model such that `y` is approximated as `y = X @ coef_.T + intercept_`." For that to be true `intercept_` would have to be `y_mean - x_mean @ coef_.T` (as in `LinearRegression`); instead it is the raw target mean and `predict` centres X first. Verdict: documentation bug (the attribute is a target mean, not the intercept of the stated linear model); it has existed since `intercept_` was introduced (1.1) and survived the 1.3 transposition and the 1.5 `/x_std` fix.

### 9. `IsotonicRegression single distinct X with out_of_bounds='nan': predictions outside the (degenerate) training domain are NaN` — all builds

Measured: `IsotonicRegression().fit([2, 2, 2], [1, 2, 6]).predict([0, 2, 5])` returns `[3.0, 3.0, 3.0]`; `X_thresholds_ = [2.0]`, `y_thresholds_ = [3.0]` (the pooled mean 3.0 at X = 2 is right). Library: `isotonic.py::_build_f` lines 305–306: `if len(y) == 1: # single y, constant prediction; self.f_ = lambda x: y.repeat(x.shape)`, which ignores `out_of_bounds`; `_transform` only clips for `"clip"` and relies on `interp1d(bounds_error=...)` for `"raise"`/`"nan"`, so with one threshold neither `nan` nor `raise` can act. Documentation (line 207): "out_of_bounds: Handles how `X` values outside of the training domain are handled during prediction. - 'nan', predictions will be NaN. ... - 'raise', a ValueError is raised." Verdict: minor bug / undocumented special case (a single distinct training X silently switches to a constant extrapolator for every `out_of_bounds` mode). All builds.

### 10. `GPC restarts: initial thetas are within the (log) bounds and roughly uniform there ('sampled log-uniform randomly from the space of allowed theta-values')` — all builds

Measured with a callable optimizer that records `initial_theta`: for `ConstantKernel(1, (1e-2, 1e2)) * RBF(1, (1e-2, 1e2))` (log-bounds ±4.605) and 300 restarts, `GaussianProcessRegressor` samples thetas in [-4.58, 4.59] with 47–53 % below the midpoint (ok), whereas `GaussianProcessClassifier` samples thetas in [0.01, 98.9]: none below the midpoint, 33 % *outside* the upper bound, and 34 of the 300 evaluations raised `LinAlgError` (the kernel amplitude/length-scale is exp(theta) up to exp(99), the Laplace Newton step's Cholesky fails). Library: `gaussian_process/_gpc.py` line 243 `theta_initial = np.exp(self.rng.uniform(bounds[:, 0], bounds[:, 1]))` versus `_gpr.py` line 330 `theta_initial = self._rng.uniform(bounds[:, 0], bounds[:, 1])`; `bounds` and `theta` are both already log-transformed (`Kernel.bounds` returns `np.log(...)`), so the `np.exp` is spurious. Documentation (lines 85, 570): "the remaining ones (if any) from thetas sampled log-uniform randomly from the space of allowed theta-values." With the default `fmin_l_bfgs_b`, scipy clips the out-of-bound starts to the upper bound, so in practice the GPC restarts explore only hyperparameter values >= exp(0.01) ≈ 1 up to the upper bound, a third of them starting exactly at the upper bound, and never the lower part of the allowed range; with a user-supplied optimizer the objective is evaluated outside the bounds and can raise. Verdict: bug, present since at least 1.1.3 and still in main.

## Observations that are not FAILs but worth recording

* `graphical_lasso(..., return_costs=True)` reports the objective as `tr(SK) - log det K + alpha ||K||_offdiag_1 + 2 p log(2 pi)` (`_graph_lasso.py::_objective` line 51: `-2 * log_likelihood + p * log(2 pi)`, where `log_likelihood` already contains `-p log(2 pi)/2`, i.e. a constant shift of 2 p log(2 pi) = 18.379 for p = 5); the docstring calls it "the objective function". The check is written with the shift and passes. With the default `enet_tol = 1e-4` the objective is not monotone (`objective monotone: False` line) and the dual gap stalls around 1e-5–1e-4, which is why the tight-tolerance checks use `enet_tol=1e-12`.
* `GraphicalLasso(alpha=0)` is accepted in 1.1.3 and 1.3+ (early return, precision = inverse empirical covariance, verified) although all docstrings say "Range is (0, inf]"; 1.2.2 rejects it with `InvalidParameterError` (`Interval(Real, 0, None, closed="right")`). Version-aware check.
* `MinCovDet.dist_` is documented as "Mahalanobis distances" but is the *squared* distance (equal to `mahalanobis(X)`, whose docstring says squared); the check passes as squared.
* `GaussianProcessRegressor(normalize_y=True).log_marginal_likelihood_value_` is the LML of the standardised targets without the `-n log(std)` Jacobian term (values printed); the docstring only says "the log-marginal-likelihood of kernel_.theta". Recorded as a passing check on the standardised-target closed form.
* `KernelRidge(kernel="rbf")` on data with a 1e5 feature offset deviates 1.3e-6 from the translation-invariant solution (2e-10 at 1e3): `rbf_kernel` uses the `||x||^2 + ||y||^2 - 2 x.y` expansion of `euclidean_distances`; the GP kernels (pdist/cdist on differences) show 1e-12 at 1e4. Check tolerance set to 1e-4.
* PLS power-method attributes agree with the SVD variants only to about sqrt(tol) (2e-8 for tol = 1e-14), because the stopping rule is `||u_i - u_{i-1}||^2 < tol` as documented; the nipals-vs-svd and PLSSVD-vs-PLSCanonical equivalences are checked at 1e-6 (and exactly for `algorithm="svd"`).
* `PLSSVD.transform` docstring has the return description inverted ("The transformed data X_transformed if `y is not None`, (X_transformed, y_transformed) otherwise"); behaviour is the sensible one and is what the harness checks.
* PLS 1-D `y`: `predict` returns (n, 1) before 1.3 and (n,) from 1.3 (changelog); `coef_` conventions: (n_features, n_targets) scaled-X coefficients < 1.3; (n_targets, n_features) scaled-X coefficients in 1.3–1.4; original-unit coefficients from 1.5 (v1.5 changelog "coef_ ... now takes into account both the scale of X and Y"). All three are verified against the NIPALS reference.
* MinCovDet correction changed in 1.8 (PR 32117): 1.1.3–1.5.2 multiply the raw covariance by `median(dist)/chi2.isf(0.5, p)` and the reweighted covariance by nothing; 1.9.1 uses the Croux/Pison consistency factors `alpha / chi2_{p+2}(chi2_p^{-1}(alpha))` for both steps. Both pipelines are re-implemented with mpmath chi-square quantiles and reproduce `covariance_`, `location_`, `support_`, `dist_` to 1e-16.

## What held up (all builds unless noted)

* `empirical_covariance` / `EmpiricalCovariance`: exact rational MLE covariance (divisor n), `assume_centered` = X^T X/n, docstring example, 1-D input treated as one sample with the warning, `location_`, `precision_` = exact inverse, `store_precision=False`, `mahalanobis` = exact squared distance, `score` = sample mean of the Gaussian log-density (mpmath), `log_likelihood` closed form, `error_norm` frobenius/spectral/scaling/squared, float32 and 1e6-offset behaviour.
* `shrunk_covariance` / `ShrunkCovariance`: exact convex combination, endpoints 0 and 1, stacked matrices (1.5+).
* Ledoit–Wolf: `ledoit_wolf_shrinkage`, `LedoitWolf`, `ledoit_wolf` equal the exact rational Ledoit & Wolf (2004) `min(bbar^2, d^2)/d^2` and `(1-s)S + s m I`; `block_size` 1/2/3/1000 identical to 1e-13; `assume_centered=True` on uncentred data; single feature -> 0; iid N(0, I) with n = 20000 gives shrinkage 1.0 (user-guide caveat); float32/offset.
* OAS: the implemented (documented) formula holds exactly in rational arithmetic; denominator-0 case -> shrinkage 1; single feature -> 0; `assume_centered`; `oas` function.
* MinCovDet p >= 2: FastMCD finds the global minimum-determinant subset (brute force over 2002 subsets), support sizes `ceil((n+p+1)/2)` and `int(support_fraction n)`, raw estimates = MLE of the support, correction + reweighting pipeline, `support_`, `location_`, `dist_`, `mahalanobis(X_train) == dist_`, `assume_centered`, 1e6 offset, float32.

* GraphicalLasso: `precision_` for alpha in {0.05, 0.2} x mode in {cd, lars} matches an independent ADMM solution of the documented objective within 1e-5 and satisfies the KKT conditions of the off-diagonal-penalised problem (unpenalised diagonal `W_ii = S_ii`, `|W_ij - S_ij| <= alpha`, `= alpha sign(K_ij)` on the support) to 1e-6; `covariance_ = precision_^{-1}`; alpha above `alpha_max` gives a diagonal precision; `return_costs` objective/dual gap recomputed; convergence at default tolerances; `covariance="precomputed"` (1.3+); offset invariance. ## Not checked / limitations

* GraphicalLassoCV split scores for alpha > 0 are not recomputed independently: the CV path runs the inner solver with `max_iter = int(0.1 * max_iter)` and warm starts along the path, so reproducing the exact numbers would mean re-implementing the library's iteration schedule; only the alpha = 0 row (plain EmpiricalCovariance) and the aggregation columns are verified.
* FastMCD for n > 500 (the subset/merge stages of `fast_mcd`) is exercised only indirectly; the brute-force MCD comparison is limited to n = 14, p = 2 (2002 subsets) and the 1-D case. The finding in the 1-D branch is exact, but no claim is made about how far FastMCD is from the optimum on large data.
* `MinCovDet.reweight_covariance` return values were not called separately (they are reproduced through `fit`); `c_step`/`select_candidates` are internal.
* GPC `predict_proba` is documented as an approximation (Williams & Barber), so it is checked at 5e-3, not to machine precision; `warm_start` and `max_iter_predict` were not exercised.
* `GaussianProcessRegressor` with a non-vector kernel (`requires_vector_input=False`), `n_targets` (1.3+) and `copy_X_train=False` were not tested; `PairwiseKernel` metrics other than rbf were not tested.
* PLS `copy=False` in-place semantics and `CCA` with more features than samples (documented as unstable) were not tested.
* Isotonic: the scipy >= 1.12 `optimize.isotonic_regression` branch is the one exercised on 1.9.1 (scipy 1.17.1); the 1.1.3–1.5.2 builds use the Cython PAVA; both agree with the exact reference.

Title: UFBoot gives 100 % where the standard bootstrap gives 61 % when every alternative topology falls below the log-likelihood cutoff — expected?

**Version:** IQ-TREE multicore version 2.4.0 for Linux x86 64-bit (built from `master` @ `a00094e0` and from the v2.4.0 tag; the same lines are in iqtree3 `master`, `tree/iqtree.cpp:3854`).

**What I ran.** A 4-taxon alignment with 100 constant columns (of all four states) and one parsimony-informative column, written by the script below, then

```
iqtree2 -s one_site.fa -m JC -B 1000 -alrt 1000 -abayes --boot-trees -seed 1 -T 1
iqtree2 -s one_site.fa -m JC -b 200 -seed 1 -T 1
```

**Expected.** The informative site is present in a bootstrap replicate with probability 1 − (1 − 1/101)^101 = 63.4 %; replicates without it have the three topologies tied. So a bootstrap support around 63 % for the AB|CD split.

**Observed.** Standard bootstrap (`-b 200`): 61 %. UFBoot (`-B 1000`): **100 %**, and all 1,000 trees in `.ufboot` are the ML topology, for seeds 1, 2 and 3. (SH-aLRT 92–94 % and aBayes 0.999 on the same branch — those are expected from what the tests do.)

**Why, as far as I can tell.** The log prints `Log-likelihood cutoff on original alignment: -147.108`. The two alternative topologies, fully optimised with `-te`, have log-likelihood −153.4339 (the ML tree: −146.7254). `IQTree::saveCurrentTree` (`tree/iqtree.cpp:3553`) returns before considering a tree for any replicate when `cur_logl < logl_cutoff - 1.0`, and the cutoff is the minimum original log-likelihood among the trees currently assigned to replicates (`:2295`), i.e. the ML tree's. The alternatives are 6.3 units below, so no replicate can ever take them, and the support is 100 % regardless of how many replicates actually contain the site.

**Shrinking.** With 6 taxa (500 simulated sites plus 1, 2 or 4 sites supporting a zero-length branch) UFBoot gave 53 / 69 / 88 % against the standard bootstrap's 53 / 77 / 92 %, and on star-tree data with 4–6 taxa the two agreed to within their noise — so on ordinary data enough near-optimal trees survive the cutoff. The 100 % needs every alternative to be > 1 log-likelihood unit worse than the worst tree any replicate currently holds, which a single strongly informative site on a small alignment produces.

**Question.** Is the hard-coded `1.0` intended to be data-independent, and would a warning when a branch's NNI alternatives both fall below `logl_cutoff - 1` (they are computed anyway when `-alrt` is on) be acceptable? I have not opened an Issue because on realistic data I could not make a number change; this is a question about the approximation's documented scope.

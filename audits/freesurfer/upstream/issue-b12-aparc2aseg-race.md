Title: mri_aparc2aseg reads ASeg with MRIneighbors while the parallel loop
rewrites ASeg in place (scan-order dependence + OpenMP race)

**Summary.** In the main labeling loop of mri_aparc2aseg.cpp, the
sulcal-bank corrective re-search is gated by
`MRIneighbors(ASeg, c, r, s, Left/Right_Cerebral_Cortex) > 0`, but the same
loop overwrites ASeg voxels as it goes (ribbon correction and the final
ctx-1000/2000 segval writes). Consequences:

1. Already-processed cortex neighbors no longer equal 3/42, so voxels on
   the trailing edge of cortex in scan order skip the corrective dot-check
   re-search that leading-edge voxels get - a systematic scan-direction
   asymmetry at exactly the ambiguous boundary voxels.
2. The loop is `#pragma omp parallel for` over columns, and MRIneighbors
   reads voxels in adjacent columns being written concurrently by other
   threads: aparc+aseg boundary labels can differ run to run with >1
   thread (non-atomic float writes read mid-update are formally undefined).

A companion PR (fix/aparc2aseg-stale-state) fixes the separate stale-state
fall-through in the winner selection; this issue covers the remaining
gating problem, which needs a design decision: the clean fix is to take a
snapshot of the segmentation after the ribbon-correction pass and gate all
MRIneighbors tests on the snapshot (two-pass structure), so gating no
longer depends on scan order or thread timing.

**Repro suggestion:** run mri_aparc2aseg twice on the same subject with
OMP_NUM_THREADS=1 vs 8 and diff the outputs; and compare a run against a
version iterating columns in reverse order.

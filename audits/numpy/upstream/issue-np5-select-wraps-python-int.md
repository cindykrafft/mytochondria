Title: BUG: np.select silently wraps an out-of-range Python int default/choice into the result dtype (300 -> 44 in int8)

_**Fact sheet, not for pasting as is.** NumPy's AI policy asks that issue descriptions not be generated by AI. The fields below follow `bug-report.yml`; the reproducer and its output can be pasted verbatim, the prose is to be written by the submitter in their own words._

**Describe the issue:**

Facts to put in your own words:

- With an `int8` choice array, `np.select(..., default=300)` returns an int8 array in which 300 has become 44. There is no warning and no error. `default=-129` gives 127. A Python int among the *choices* wraps the same way (`np.select([c, ~c], [300, np.int8(1)])` gives `[44, 1]`).
- Under NEP 50 a Python int is "weak", so the result dtype is int8. An out-of-range weak int should then raise `OverflowError`, as `int8_array + 300` does. `np.where` had exactly this bug. It was fixed in 2.5.0 ("`numpy.where` no longer truncates Python integers ... Now, an OverflowError will be raised", gh-30803), and on `main` `np.where(c, x, 300)` raises while `np.select` still wraps.
- On 1.23–1.26 the result is promoted to int16 and holds 300.
- Where it happens (`numpy/lib/_function_base_impl.py`, `select`): Python scalars are kept as Python scalars, so `np.result_type(*choicelist)` weakly picks int8. They are then broadcast to arrays, and `result = np.full(result_shape, choicelist[-1], dtype)` followed by `np.copyto(result, choice, where=cond)` fill the result. `np.full` goes through `copyto(..., casting='unsafe')`, so the value is truncated. By then it is an int64 array, not a Python int, so the NEP 50 overflow check never sees it.
- The docstring says `default`: "The element inserted in `output` when all conditions evaluate to False".

**Reproduce the code example:**

```python
import numpy as np

c = np.array([True, False])
x = np.array([1, 2], dtype=np.int8)
print(np.select([c], [x], default=300))
print(np.select([c], [x], default=-129))
print(np.select([c, ~c], [300, np.int8(1)]))
print(np.where(c, x, 300))
```

**How does this issue affect you or how did you find it:** (your own words) Found by a harness that compares `select` / `where` / `piecewise` against plain-Python evaluation (`audits/numpy/verify/n11_stats_reductions_convolution.py` in https://github.com/cindykrafft/mytochondria). Impact: a common idiom is `np.select(conditions, choices, default=<sentinel>)` with small-integer label or count arrays, for example a sentinel like 999 or -1000 in uint8/int8 data. The sentinel changes value silently, and it can collide with real labels (300 -> 44).

**Possible fix (not prepared):** validate Python-int choices and `default` against the result dtype before broadcasting, the way `np.where` does since gh-30803. Alternatively, fill with `casting='same_kind'` and let the scalar conversion raise.

Title: BUG: np.unique(..., equal_nan=False) merges NaT values for datetime64 when no optional output is requested

**Describe the issue:**

Facts to put in your own words:

- `np.unique(a, equal_nan=False)` on a `datetime64` array with two NaT returns one NaT. The same call with `return_counts=True` (or `return_index` / `return_inverse`) returns two, and so does every 1.x release for both forms. The docstring says `equal_nan`: "If True, collapses multiple NaN values in the return array into one", so with `False` the NaTs should stay separate, as float NaN does on every path.
- `timedelta64` is not affected. Float NaN is not affected either.
- Cause: since the hash-based path (gh-26018, 2.3; more dtypes in gh-29537, 2.4), the call without optional outputs goes through `_unique_hash`. In `numpy/_core/src/multiarray/unique.cpp`, `NPY_DATETIME` is registered with `unique_numeric<npy_uint64, hash_integer<npy_uint64>, equal_integer<npy_uint64>>`. `equal_integer` is `*lhs == *rhs` and ignores `equal_nan`, so two NaT, which have the same bit pattern, always land in one bucket. The sorting path uses `aux[1:] != aux[:-1]` (NaT != NaT is True) and collapses NaT only in its `equal_nan` branch for kinds `"cfmM"`.
- Same file, same mechanism, for complex with `equal_nan=True` (the default). The docstring (Notes, versionchanged 1.21) says the representative of the NaN class is "the smallest one in the lexicographical order". The hash path keeps the first one it meets instead, so `np.unique(c)` and `np.unique(c, return_counts=True)[0]` give different values. This is related to, but not the same as, gh-30113 (the first-occurrence index with `return_index`).

**Reproduce the code example:**

```python
import numpy as np

a = np.array(['2020-01-01', 'NaT', '2020-01-01', 'NaT'], dtype='datetime64[D]')
print(np.unique(a, equal_nan=False))
print(np.unique(a, equal_nan=False, return_counts=True))

c = np.array([complex(np.nan, np.nan), complex(np.nan, -3), 1+1j, complex(2, np.nan)])
print(np.unique(c), np.unique(c, return_counts=True)[0])
```

What it affects: counting the distinct values of a datetime column (`len(np.unique(a, equal_nan=False))`) gives a different answer depending on whether counts are also requested, and a different answer from 1.x.

**Fix (for the PR, after the issue is open):** branch `fix/unique-hash-nat-complex-nan`, patch `0001-BUG-unique-hash-path-honour-equal_nan-for-NaT-pick-t.patch` in this directory, one commit on `main` @ 55511445dc. It gives `unique_numeric` a NaN predicate and a less-than for the type. With `equal_nan`, the NaN-like values stay out of the hash set and the smallest one in sort order is appended. NaT is the NaN-like value of datetime64 and compares equal only under `equal_nan`. It adds two tests (`test_unique_datetime_nat_equal_nan`, `test_unique_complex_nan_representative`, 4 cases fail without the change), and `test_arraysetops.py` + `test_datetime.py` pass (643 passed). Open PRs that also touch `unique.cpp` and should be mentioned in the PR: #30281 (first NaN index for complex) and #30496 (hash path with return_index/inverse/counts).

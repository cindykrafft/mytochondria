### PR 1 — `fix/unique-hash-nat-complex-nan` — "BUG: unique hash path: honour equal_nan for NaT, pick the sorted NaN representative for complex"

**PR summary (facts):**
- Closes the NP3 issue (#NNN, to be opened first from `issue-np3-unique-nat-equal-nan.md`).
- `unique.cpp`: `unique_numeric` gets two more template parameters, a NaN predicate and a less-than
  for the element type. With `equal_nan`, values the predicate marks as NaN-like are not inserted into
  the hash set. The smallest of them (by the less-than) is appended once at the end. Without
  `equal_nan`, each one is appended.
- datetime64: `isnan_datetime` tests for `NPY_DATETIME_NAT`. `equal_datetime` treats two NaT as equal
  only under `equal_nan`. Result: `equal_nan=False` keeps every NaT, as the sorting path and 1.x do.
- complex: `less_complex` mirrors `complex_type::less` in `numpy_tag.hpp`, the order `np.sort` uses
  (NaN last: `R+Rj < R+nanj < nan+Rj < nan+nanj`). The representative is then the smallest in the
  lexicographic order, as the docstring's Notes say.
- The other registered dtypes pass `isnan_never`, so their behaviour and speed are unchanged.
- Tests (`numpy/lib/tests/test_arraysetops.py`): `test_unique_datetime_nat_equal_nan`, and
  `test_unique_complex_nan_representative` parametrised over complex64/complex128. 4 cases fail on
  unmodified `main`. `test_arraysetops.py` + `_core/tests/test_datetime.py`: 643 passed with the
  change, on a source build of `main` @ 55511445dc (Python 3.12).
- Related open PRs touching the same file: #30281 (first NaN index for complex, gh-30113) and
  #30496 (hash path with return_index/inverse/counts). This change is independent of both, but
  mention them so the reviewers can order the merges.

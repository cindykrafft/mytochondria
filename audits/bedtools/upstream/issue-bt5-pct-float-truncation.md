Title: slop -pct / flank -pct lose one base at some percentages; absolute -l/-r/-b round above 2^24

**bedtools version:** master @ 614e9a5; reproduced on v2.31.1 and v2.30.0.

**What happened.** `slop -pct` and `flank -pct` compute the slop as a
single-precision `float` product and truncate, so at percentages where
`pct * size` is an exact integer that the float product lands just below, one base
is lost. The absolute `-l/-r/-b` values are also stored `float`, so values above
2^24 = 16,777,216 are rounded.

```bash
printf 'chr1\t100000000\n' > g.genome
printf 'chr1\t1000000\t1000100\n' > a.bed        # a 100-bp feature

bedtools slop  -i a.bed -g g.genome -b 0.53 -pct  # got 1000053 added? no: 948..1052 (52 each side; expected 53)
bedtools flank -i a.bed -g g.genome -l 0.53 -r 0 -pct  # flank length 52 (expected 53)

printf 'chr1\t25000000\t25000010\n' > a.bed
bedtools slop -i a.bed -g g.genome -b 20000001   # got 5000000..45000010 (float32(20000001)=20000000); expected 4999999..45000011
```

**What shrinking the example showed.** 12 of the 99 whole-percent values are
affected at some feature size <= 20000 (0.13, 0.21, 0.26, 0.39, 0.42, 0.52, 0.53,
0.59, 0.65, 0.71, 0.78, 0.84); the common 0.10/0.25/0.50 are exact. On the shipped
binary, 36/36 tested (pct, size) cases lose exactly one base in both `slop -pct`
and `flank -pct`.

**Cause.** `slopBed.cpp:57-60,87-88` and `flankBed.cpp:57-58` multiply in
`float` and cast to `CHRPOS`; `_leftSlop`/`_rightSlop` are `float` fields.

**Fix.** Compute the fractional slop in `double` and round (rather than truncate a
float), and carry the absolute slop as an integer. This changes the option-parsing
signatures in `slopMain`/`flankMain`, so it is left for a follow-up PR; filing the
finding for tracking.

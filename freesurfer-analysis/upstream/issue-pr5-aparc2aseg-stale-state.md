Title: mri_aparc2aseg: voxels whose surface candidates are all rejected
inherit the previous voxel's ROI and hemisphere (uninitialized annotid)

**Summary.** In the main labeling loop of `mri_aparc2aseg.cpp`, the winner
variables are declared once per column
(`int annot=0,annotid,hemi=0,segval=0;` — note `annotid` uninitialized;
dev ~line 550) and the four closest-surface winner blocks use strict
comparisons (~lines 785-815). When every candidate is rejected — all four
distances forced to 1e15 by the sulcal-bank BRFdotCheck logic, or a
hemisphere disabled with --lh/--rh — no winner block executes, and the
voxel keeps `annot/annotid/hemi/dmin` from the previously processed voxel
in the column. In v6.0.0 these were file-scope globals, so the stale value
could come from anywhere in the scan.

**Impact.** The affected voxels are exactly the ambiguous sulcal-bank
voxels the dot checks target, so stale labels land in systematic locations:
a voxel can receive an unrelated ROI, or a ctx-lh label on a
right-hemisphere voxel, depending only on scan order — and at the first
such voxel of a column, `annotid` is read uninitialized (undefined
behavior). Biases aparc+aseg and wmparc ROI volumes at boundaries.

**Affected versions:** v6.0.0 through dev (mechanism differs slightly:
globals in v6, per-column in v7+).

A fix (per-voxel state reset routing no-winner voxels into the existing
"unknown" handling) is available: https://github.com/freesurfer/freesurfer/compare/dev...cindykrafft:freesurfer:fix/aparc2aseg-stale-state
A related but separate problem — the MRIneighbors gating reads ASeg while
the same parallel loop rewrites it (scan-order dependence + OpenMP race) —
is filed separately, as it needs a two-pass restructure.

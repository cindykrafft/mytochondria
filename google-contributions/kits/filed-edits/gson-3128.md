## Why edit

1. **Class A, already raised by the maintainer: paraphrase of a code comment.**
   - Before: "The code comment assumes that any string the regex lets through which is not a valid IP literal is rejected by `getByName` without a lookup."
   - Evidence: the comment at `TypeAdapters.java:764-767` (854c825) says: "A pattern that matches every IP address and no DNS address. It matches plenty of things that aren't either of those, which is fine. ... (There are further constraints in both cases, but they don't matter here.)" It says nothing about a lookup.
   - The reply draft already handles this, so the body needs no change beyond the optional note.

2. **Class A: the description of JDK behavior is wrong for `300.1.1.1`.** This error is in both the body and the reply draft.
   - Body: "`InetAddress.getByName` treats the string as a literal only if it is a valid IPv4 literal, or if it starts with a hex digit, `:` or `[`. Everything else goes to the name service."
   - Reply draft: "For those two strings, `InetAddress.getByName` doesn't take the literal-parsing path, because that path only handles strings starting with `[`, a hex digit or `:`."
   - Evidence, JDK 21 `InetAddress.java`:
     - The literal branch at 1635-1636 is `if (IPAddressUtil.digit(host.charAt(0), 16) != -1 || (host.charAt(0) == ':'))`. `'3'` is a hex digit, so `300.1.1.1` does enter it.
     - `validateNumericFormatV4` (1644) returns null for it.
     - `textToNumericFormatV6` returns null.
     - The throw at 1661-1663 only fires if the host `contains(":")` or `ipv6Expected`.
     - So it falls out of the branch to `return getAllByName0(host, true, true);` (1688).
     - `zz:1` never enters the branch, because `'z'` is not a hex digit.
   - The conclusion (both strings reach the name lookup) is still correct. Only the stated reason is wrong for `300.1.1.1`.
   - Re-run on 2026-09-24 with the base classes (JDK 21.0.10, `-Djdk.net.hosts.file` mapping both strings):
     ```
     inet evil.example.com -> com.google.gson.JsonSyntaxException: Failed parsing 'evil.example.com' as InetAddress; ...
     inet 300.1.1.1 => 300.1.1.1/10.9.9.9
     inet zz:1 => zz:1/10.8.8.8
     ```
     Without the hosts file, both fail with `UnknownHostException: ...: Name or service not known`.

3. **Class B, optional, not worth an edit on its own.**
   - Before: "the lookup fails with `UnknownHostException: 300.1.1.1: Name or service not known`, after a real resolver query."
   - The message shows that the system resolver was called (`getaddrinfo`'s EAI_NONAME text). We didn't capture a DNS packet, so "a real resolver query" goes further than we checked. If this is ever touched, change it to "from the system resolver".

Class C (fine):
- The regex quote (`TypeAdapters.java:768`).
- The reproduction and its output (re-run above).
- The fix suggestion. In my testing on JDK 21, `a:b` and `[zz:1]` throw `invalid IPv6 address literal`, and `01.2.3.4` and `1.2.3.04` parse as literals.
- The #3075 summary is close to that PR's text: "Resolving names like that can be expensive, and given that the canonical serial form is numeric, Gson should not do it by default."
